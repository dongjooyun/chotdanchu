# 테스트 체계

등급이 왜 그렇게 나왔는지 **근거를 하나씩 확인할 수 있게** 설계했다. 설계 방식은 ISTQB 테스트 설계 기법을 따른다.

## 한눈에 보기

| 수준 | 도구 | 무엇을 | 위치 | 실행 |
|---|---|---|---|---|
| 단위 | Vitest | 등급 계산, 역량 매칭 | `tests/unit/indicators.test.ts`, `competencies.test.ts` | `npm test` |
| 통합 | Vitest | 채팅 API 요청 하나의 응답 (위젯, 로그, 상태 코드) | `tests/unit/chat-api.test.ts` | `npm test` |
| 회귀 | Vitest | 목업 30곳 등급 분포를 지금 동작대로 고정 | `tests/unit/indicators.regression.test.ts` | `npm test` |
| 통합 (에이전트) | Vitest + 가짜 LLM | 도구 호출 순서, 호출 상한 8회, 판단 로그, 폴백, 개인정보 | `tests/unit/agent.test.ts` | `npm test` |
| 단위 (실데이터 변환) | Vitest + 고정 파일 | OpenDART, 국민연금 응답을 원시값으로 바꾸는 계산이 공시 원본과 맞는지 | `tests/unit/real-data.test.ts`, `tests/fixtures/real/` | `npm test` |
| 단위 (하는 일 세 줄 요약) | Vitest + 가짜 fetch, 가짜 LLM | 세 줄 고르기와 숫자 문장 제외, 공시 없음과 확인 불가의 구분, 카드 표시, 원문 추출, 오류 처리, 캐시 | `tests/unit/business-summary.test.ts`, `company-summary-card.test.ts`, `real-business-overview.test.ts`, `summarize-llm.test.ts` | `npm test` |

- 사용 현황 (2026-11-22): 단위·통합·회귀 405개(에이전트 14개, 리포트 초안 8개, 실데이터 변환 18개, 하는 일 세 줄 요약 90개 포함), E2E 12개 x 화면 2종 = 24개

- 각 테스트 이름 맨 앞이 케이스 ID다 (예: `IND-FH-G-03`). `npm run test:verbose`로 ID와 입력, 기대 등급이 한 줄씩 보인다

## 쓰는 테스트 설계 기법

| 약어 | 기법 | 어디에 쓰나 | 예 |
|---|---|---|---|
| EP | 동등 분할 | 같은 결과가 나올 구간마다 대표값 하나 | 부채비율 50% (A 구간), 200% (B 구간), 500% (C 구간) |
| BVA | 경계값 분석 (3점) | 기준선의 바로 아래, 정확히 그 값, 바로 위 | 부채비율 99.99% A, 100% B, 100.01% B |
| DT | 결정 테이블 | 조건이 둘 이상 겹칠 때 조합마다 하나 | 투자 단계 = (금액 조건 충족?) x (최근 18개월?) 네 조합 |
| EG | 오류 추정 | 값이 비었거나 이상할 때 | 상태는 ok인데 값이 null, 업종 평균이 없는 보상 |
| 회귀 | 회귀 테스트 | 고친 뒤 기존 동작이 안 바뀌었는지 | 목업 30곳 등급 분포 |
| 상태 전이 | 상태 전이 테스트 | 채팅 단계가 순서대로 넘어가는지 | 첫 방문, 직무 선택, 회사 입력, 후보 선택, 기업 카드, 리포트 |

## 케이스 ID 규칙

- 등급 계산: `IND-{기준표 행}-{번호}`
  - 기준표 행 약어: `FH` 재무 체력, `GR` 성장성, `PF` 수익성, `HR` 고용 흐름, `CP` 보상, `TN` 근속, `TI` 기술 투자, `FS` 투자 단계, `RK` 리스크, `TR` 정보 투명도, `EG` 오류 추정
  - 뒤의 `-G`는 일반 기업 기준표, `-S`는 스타트업 기준표
- 역량 매칭 `CMP-*`, 채팅 API `API-*`, 에이전트 루프 `AGT-*`, 리포트 카드 초안 `RPT-*`, 맞대결 `MAT-*`, 카드 표시 `BRD-*`, 세션(카드 모음) `SES-*`, 실데이터 변환 `REAL-*`, 회귀 `REG-*`, 화면 흐름 `E2E-*`

## 추적성: 기준표의 행 하나 = 테스트 묶음 하나

- 원본은 `tests/unit/criteria-registry.ts`. `docs/indicators.md` 기준표의 한 줄이 여기 한 줄이다
- 자동 검사 `IND-TRACE-01~03`이 아래를 확인한다
  - 모든 테스트 케이스가 등록된 기준표 행에 속한다
  - 모든 기준표 행에 테스트가 있고, 경계값(BVA) 케이스가 행마다 정한 개수 이상이다
  - 구간형 기준은 A, B, C 세 등급이 모두 검증된다
- **기준표에 새 행을 넣고 registry에 안 넣거나, 행을 넣고 테스트를 안 만들면 테스트가 실패한다**

| 기준표 행 | 케이스 | 경계값 (BVA) 핵심 |
|---|---|---|
| 재무 체력 일반 (부채비율) | `IND-FH-G-*` | 100% 미만 A, 100~300% B, 300% 이상 C |
| 재무 체력 스타트업 (런웨이) | `IND-FH-S-*` | 18개월 이상 A, 12~18개월 B, 12개월 미만 C |
| 성장성 일반 / 스타트업 | `IND-GR-G-*`, `IND-GR-S-*` | 15% / 50% 이상 A, 0 이상 B, 감소 C |
| 수익성 일반 (영업이익률) | `IND-PF-G-*` | 7% 이상 A, 3% 이상 B |
| 수익성 스타트업 (영업이익 방향) | `IND-PF-S-*` | 0 이상 A, 적자 축소 B, 같거나 확대 C |
| 고용 흐름 일반 / 스타트업 | `IND-HR-G-*`, `IND-HR-S-*` | 순증 여부 x 퇴사율(연 20%, 월 3%, 월 5%) |
| 보상 | `IND-CP-*` | 업종 평균 +10% 이상 A, -10% 이하 C |
| 근속 | `IND-TN-*` | 10년 이상 A, 5년 이상 B |
| 기술 투자 일반 | `IND-TI-G-*` | 업종 구간 4개 각각의 상한과 하한 |
| 기술 투자 스타트업 | `IND-TI-S-*` | 등록 특허 3건 이상 A, 1~2건 B, 0건 C |
| 투자 단계 | `IND-FS-S-*`, `IND-FS-G-*` | 금액 조건 x 18개월 조건, 일반 기업은 항상 등급 없음 |
| 리스크 | `IND-RK-*` | 해당 없음 A, 경미 B, 해당 C |
| 정보 투명도 | `IND-TR-*` | 확인 7개 이상 A, 4개 이상 B (일반 기업은 8개 중) |
| 확인 불가 처리 | `IND-EG-*` | 이유(`not_disclosed`, `no_source`, `fetch_failed`)가 그대로 전달 |
| 업종 구간 (KSIC) | `IND-KSIC-*` | 코드 12개가 4개 구간으로 나뉜다 |

## 근거 확인: 테스트가 보증하는 것

- 등급이 나온 칸은 "어느 기준으로 매겼는지"(근거 문구)가 비어 있지 않고, 기준값이 문구에 들어 있다
- 값이 없으면 등급을 주지 않고 이유를 반드시 붙인다 (일반 기업의 투자 단계만 "등급 없음"이라 이유 없음)
- 경계값은 "N 이상" 쪽 등급이다 (부채비율 정확히 100% = B, 매출 증가율 정확히 15% = A)
- 퇴사율을 모르면 고용 흐름은 A가 될 수 없다 (최대 B)
- 같은 입력이면 항상 같은 결과다

## 테스트가 정말 버그를 잡는지 (변이 확인, 2026-11-20)

기준 코드를 일부러 한 곳씩 틀리게 바꿔서 테스트가 실패하는지 봤다. 5곳 모두 실패로 잡혔다.

| 일부러 낸 버그 | 결과 |
|---|---|
| 부채비율 경계 `< 100`을 `<= 100`으로 | 잡힘 (1개 실패) |
| 스타트업 영업이익 0을 흑자로 안 침 | 잡힘 (1개 실패) |
| 보상 +10% 경계 `>=`를 `>`로 | 잡힘 (1개 실패) |
| 정보 투명도 A 기준 7개를 8개로 | 잡힘 (2개 실패) |
| 투자 18개월 경계 `<=`를 `<`로 | 잡힘 (2개 실패) |

## 에이전트 루프 테스트 (AGT, 2026-11-20)

LLM 응답을 가짜로 바꿔 넣어서 크레딧 없이 루프의 규칙을 검사한다.

| 케이스 | 기법 | 확인하는 것 |
|---|---|---|
| AGT-01~03 | 상태 전이 | 후보 1곳이면 바로 카드, 2곳이면 후보 칩, 도구 없이 답하면 그 문장 |
| AGT-04~06 | 경계값 | 호출 8회까지 실행, 9회째에서 멈추고 `limit` 로그. 한 응답의 도구 여러 개도 각각 센다 |
| AGT-07~11 | 오류 추정 | 없는 도구, 잘못된 인자, API 연결 실패, 알 수 없는 오류, 거절. 전부 멈추지 않고 대신 답한다 |
| AGT-12~14 | 규칙 | 카드 숫자는 코드 계산과 같고 LLM 문장이 섞이지 않는다. LLM에 대표자 이름을 보내지 않는다. 강제 도구 선택 없음 |

- 변이 확인: 상한 비교를 `>`에서 `>=`로, 도구 결과에 대표자 이름 추가, 오류 표시(`is_error`) 끄기. 3곳 모두 잡혔다
- 실제 API는 테스트에서 부르지 않는다. 사람이 `USE_AGENT=true`로 켜서 확인한다

## 하는 일 세 줄 요약 테스트 (BS, SUM, RBO, LLM, 2026-11-22)

외부 API와 실제 LLM은 부르지 않는다. 가짜 fetch, 직접 만든 ZIP, 가상 원문 조각, 가짜 LLM으로 검사한다 (이 문서 기준 90개). 실제로 실행한 결과 파일은 모양만 지킨다 (SUM-16~19).

| 케이스 | 기법 | 확인하는 것 |
|---|---|---|
| BS-01~06 | 동등 분할, 오류 추정 | 문장 나누기(소수점은 안 자름), 숫자 문장 제외, 중복 문장, 빈 문단 |
| BS-07 | 경계값 | 수치 없는 문장이 0, 2, 3, 4개일 때 줄 수 |
| BS-08~11 | 규칙 | 목업 상장 5곳은 3줄 + 가상 링크, 요약 줄은 원문 문장 그대로이고 숫자 없음, 나머지 25곳은 공시 없음 |
| BS-12~15 | 결정 | 실데이터: 저장된 요약, 공시 없음, 아직 계산 안 함(확인 불가)이 서로 구분됨 |
| BS-16~18 | 캐시 | 같은 기업은 한 번만 계산, 확인 불가는 캐시하지 않음 |
| SUM-01~08 | 통합 | 채팅 응답에 요약이 실림, 공시 없음은 `info` 로그라 지표의 확인 불가 개수가 그대로, 후보 칩 경로, 실데이터 모드 |
| SUM-09~12 | 화면 | 카드 문구: 요약 3줄과 링크, 가상 링크 자리, 공시 없음, 확인 불가와 이유 |
| SUM-13~15 | 실데이터 | 사전 계산 파일의 값(요약, 공시 없음)이 카드에 반영되고, 없는 기업은 확인 불가 |
| SUM-16~19 | 규칙 | 실제 결과 파일(`data/real/business-summaries.json`)을 지킨다: 시연 기업 4곳이 모두 있음, 요약은 3줄이고 숫자가 없음, 링크는 DART 공시 주소, 확인일과 방식 형식, 원문은 저장하지 않음(항목에 상태/요약/출처/방식만), 인증키 모양 문자열 없음 |
| SUM-20~23 | 결합, 규칙 | 새 디자인 카드(동주님, PR #18)와 요약 블록이 함께 있다: 요약은 지표 펼치기 아래/저장 버튼 위에 한 카드 안에 있고, 저장 후에도 요약이 그대로이며 주 버튼은 하나, 요약 블록은 새 디자인 클래스(`cc-biz`)를 쓰고 옛 와이어프레임 클래스가 없음, `.cc-biz` 스타일은 디자인 규칙(토큰만, 그림자와 그라데이션 없음, 1px 회색 선, 모서리 4px)을 지킴 |
| RBO-01~08 | 동등 분할, 경계값 | 목차는 건너뛰고 본문이 있는 "사업의 개요" 추출, 하위 항목 포함, 업종 괄호가 붙은 제목(`1. (제조서비스업)사업의 개요`, 카카오 실측, RBO-05b/05c), 표 제외, 본문 최소 30자, 최대 4000자 |
| RBO-09~15 | 오류 추정 | 태그와 엔티티 정리, EUC-KR 해석, ZIP 읽기(저장/deflate), 깨진 ZIP |
| RBO-16~26 | 오류 추정, 규칙 | 최신 사업보고서 고르기, 공시검색 013은 공시 없음, 020과 문서 오류와 네트워크 오류는 실패, 어떤 실패에도 인증키가 문구에 안 나옴, 호출은 기업당 2번 |
| RBO-27~30 | 캐시 | 저장 항목에 원문이 없음, 공시 없음 저장, 실패는 저장 안 함, 이미 저장된 기업은 건너뜀 |
| LLM-01~12 | 경계값, 규칙 | 정확히 3줄만 통과, 숫자와 주소 검증, 줄 길이 5~120자, 실패하면 규칙 요약으로 대신, 모델 이름은 config, 개요 안 지시문 주입 방어 |

- 변이 확인 (2026-11-22): 일부러 낸 버그 24개(숫자 문장 제외 끄기, 3줄 상한 변경, 중복 제외 끄기, 캐시 끄기, 확인 불가도 캐시하기, 공시 없음과 확인 불가 같게 만들기, 개요 최소 길이 변경, 최신 대신 가장 이른 공시 고르기, 013을 실패로, 오류 문구에 주소 넣기, 표 제거 끄기, 저장된 기업 다시 받기, 모델 답 검증 끄기 등)를 모두 잡았다. 처음에는 개요 최소 길이 변경을 놓쳐서(테스트가 상수를 그대로 썼음) 경계값을 숫자로 고정했다
- 그 뒤 추가한 변이 확인: 업종 괄호 허용을 뺌 1가지, 결과 파일을 일부러 어긋나게 한 6가지(요약 줄에 숫자 넣기, 줄 4개, 다른 사이트 링크, 원문 필드 추가, 키 모양 문자열 섞기, 시연 기업 빼기)를 모두 잡았다. main 병합 때 추가한 SUM-20~23도 일부러 낸 버그 6가지(요약 블록 빼기, 그림자 추가, 선 2px, 모서리 6px, 옛 클래스로 되돌리기, 직접 쓴 색)를 모두 잡았다
- 실제 DART 원문으로는 11/22 시연 기업 4곳을 실행해 "사업의 개요" 추출을 사람이 확인했다. 이 확인은 자동 테스트가 아니다. 자동 테스트(RBO)는 가상 원문 조각만 쓰고, 실행 결과 파일은 모양만 지킨다(SUM-16~19). 카카오의 제목 형식(업종 괄호)은 실행해서 처음 드러나 RBO-05b로 고정했다 (`docs/agent-design.md`)

## 합격 기준과 결함 보고

- PR 전: `npm test`, `npm run lint`, `npm run build`가 모두 통과해야 한다. 화면 흐름을 건드렸으면 `npm run test:e2e`도
- 결함을 찾으면 PR이나 이슈에 이 형식으로 적는다
  - 케이스 ID, 입력, 기대 결과, 실제 결과, 재현 순서, 심각도(상: 등급이 틀림 또는 규칙 위반, 중: 화면 깨짐, 하: 문구)
- 기준표나 등급 로직을 바꾸면 registry, 테스트, 회귀 표(`REG`)를 **같은 PR에서** 같이 고친다

## 실행 방법

```bash
npm test                # 단위·통합·회귀 (약 1초)
npm run test:verbose    # 케이스 ID와 입력, 기대 등급을 한 줄씩 보기
npm run test:e2e        # 화면 흐름 (개발 서버를 3100번 포트로 따로 띄움)
```

- E2E는 컴퓨터에 설치된 Chrome을 쓴다(내려받기 없음). Chrome이 없으면 `npx playwright install chromium` 후 `PW_CHANNEL=chromium npm run test:e2e`
- E2E 서버는 별도 빌드 폴더(`.next-e2e`)를 써서, 이미 켜 둔 `npm run dev`(3000번)와 부딪히지 않는다

### 실제 폰에서 나온 버그와 아이폰 사파리(WebKit) 테스트 (11/22 실사용 테스트 뒤)

친구와 직접 써 보니 데스크톱 크롬 E2E가 못 잡은 버그가 나왔다. 원인은 "테스트가 크롬만 돌았고, 눈으로 보이는 결과(거꾸로 된 글자, 사진 안 내용)를 확인하지 않았다"였다. 그래서 아이폰 사파리를 흉내 내는 WebKit 프로젝트(`iphone-safari`, 처음 한 번 `npx playwright install webkit`)를 두고, 실제로 보이는 값(변환 행렬, 사진 픽셀)을 확인한다. `npm run test:e2e:safari`로 이 프로젝트만 돌린다.

| 버그 | 케이스 | 확인 방법 |
|---|---|---|
| 카드를 뒤집으면 (i) 말풍선 글자가 거꾸로 보임 | `E2E-22` (PC, 모바일, 사파리) | 말풍선과 조상에 거울 변환이 없는지, 카드의 보이는 면이 평평한지, 말풍선이 화면 가로 안인지. 예전 3D 방식으로 일부러 되돌리면 실패하는 것을 확인했다 |
| 폰에서 이미지 저장이 안 됨 (공유 창을 누른 뒤 사진을 만들어 사파리가 막음) | `E2E-23` (PC, 모바일, 사파리) | 누르기 전에 사진이 준비돼 있고(`data-ready`), PC는 파일, 터치 화면은 "길게 눌러 저장" 창에 사진이 뜨며 빈 흰 사진이 아닌지 |
| 카카오톡 안에서 열면 저장, 공유가 막힘 | `E2E-24`, `E2E-24b` | 카카오톡 사용자 에이전트일 때만 "다른 브라우저로 열어 주세요" 안내와 열기 버튼이 보이는지 |

- 한계: 진짜 아이폰, 갤럭시, 카카오톡 앱 안에서의 갤러리 저장은 자동으로 확인하지 못한다. 배포 뒤 동주와 지인 폰으로 직접 확인한다(노션 "배포본 QA 시나리오"). 회사 로고가 사진에 찍히는지는 실데이터 모드에서만 볼 수 있어 수동으로 확인한다(목업 기업에는 로고가 없다)
- 저장 사진의 글꼴: 글꼴 CSS가 다른 주소(CDN)에 있어 브라우저가 읽기를 막으면 사진이 기본 글꼴로 나온다. 글꼴 링크에 `crossOrigin="anonymous"`를 붙여 읽을 수 있게 했다
