# 테스트 체계

등급이 왜 그렇게 나왔는지 **근거를 하나씩 확인할 수 있게** 설계했다. 설계 방식은 ISTQB 테스트 설계 기법을 따른다.

## 한눈에 보기

| 수준 | 도구 | 무엇을 | 위치 | 실행 |
|---|---|---|---|---|
| 단위 | Vitest | 등급 계산, 역량 매칭 | `tests/unit/indicators.test.ts`, `competencies.test.ts` | `npm test` |
| 통합 | Vitest | 채팅 API 요청 하나의 응답 (위젯, 로그, 상태 코드) | `tests/unit/chat-api.test.ts` | `npm test` |
| 회귀 | Vitest | 목업 30곳 등급 분포를 지금 동작대로 고정 | `tests/unit/indicators.regression.test.ts` | `npm test` |
| 통합 (에이전트) | Vitest + 가짜 LLM | 도구 호출 순서, 호출 상한 8회, 판단 로그, 폴백, 개인정보 | `tests/unit/agent.test.ts` | `npm test` |
| 단위 (실데이터 변환) | Vitest + 고정 파일 | OpenDART, 국민연금 응답을 원시값으로 바꾸는 계산이 공시 원본과 맞는지 | `tests/unit/real-data.test.ts`, `tests/fixtures/real/` | `npm test` |
| 시스템(E2E) | Playwright | 실제 브라우저로 처음부터 끝까지 (데스크톱 1280px, 모바일 375px) | `tests/e2e/chat-flow.spec.ts` | `npm run test:e2e` |

- 사용 현황 (2026-11-20): 단위·통합·회귀 290개(에이전트 14개, 리포트 초안 7개, 실데이터 변환 16개 포함), E2E 12개 x 화면 2종 = 24개
- E2E는 `.env.local`에 `USE_AGENT=true`가 있어도 에이전트를 끈 채로 돈다 (크레딧을 쓰지 않고 결과가 같도록)
- 각 테스트 이름 맨 앞이 케이스 ID다 (예: `IND-FH-G-03`). `npm run test:verbose`로 ID와 입력, 기대 등급이 한 줄씩 보인다

## 쓰는 테스트 설계 기법

| 약어 | 기법 | 어디에 쓰나 | 예 |
|---|---|---|---|
| EP | 동등 분할 | 같은 결과가 나올 구간마다 대표값 하나 | 부채비율 50% (A 구간), 200% (B 구간), 500% (C 구간) |
| BVA | 경계값 분석 (3점) | 기준선의 바로 아래, 정확히 그 값, 바로 위 | 부채비율 99.99% A, 100% B, 100.01% B |
| DT | 결정 테이블 | 조건이 둘 이상 겹칠 때 조합마다 하나 | 투자 단계 = (금액 조건 충족?) x (최근 18개월?) 네 조합 |
| EG | 오류 추정 | 값이 비었거나 이상할 때 | 상태는 ok인데 값이 null, 업종 평균이 없는 보상 |
| 회귀 | 회귀 테스트 | 고친 뒤 기존 동작이 안 바뀌었는지 | 목업 30곳 등급 분포 |
| 상태 전이 | 상태 전이 테스트 | 채팅 단계가 순서대로 넘어가는지 | 첫 방문, 직무 선택, 회사 입력, 후보 선택, 기업 카드, 리포트 |

## 케이스 ID 규칙

- 등급 계산: `IND-{기준표 행}-{번호}`
  - 기준표 행 약어: `FH` 재무 체력, `GR` 성장성, `PF` 수익성, `HR` 고용 흐름, `CP` 보상, `TN` 근속, `TI` 기술 투자, `FS` 투자 단계, `RK` 리스크, `TR` 정보 투명도, `EG` 오류 추정
  - 뒤의 `-G`는 일반 기업 기준표, `-S`는 스타트업 기준표
- 역량 매칭 `CMP-*`, 채팅 API `API-*`, 에이전트 루프 `AGT-*`, 리포트 카드 초안 `RPT-*`, 실데이터 변환 `REAL-*`, 회귀 `REG-*`, 화면 흐름 `E2E-*`

## 추적성: 기준표의 행 하나 = 테스트 묶음 하나

- 원본은 `tests/unit/criteria-registry.ts`. `docs/indicators.md` 기준표의 한 줄이 여기 한 줄이다
- 자동 검사 `IND-TRACE-01~03`이 아래를 확인한다
  - 모든 테스트 케이스가 등록된 기준표 행에 속한다
  - 모든 기준표 행에 테스트가 있고, 경계값(BVA) 케이스가 행마다 정한 개수 이상이다
  - 구간형 기준은 A, B, C 세 등급이 모두 검증된다
- **기준표에 새 행을 넣고 registry에 안 넣거나, 행을 넣고 테스트를 안 만들면 테스트가 실패한다**

| 기준표 행 | 케이스 | 경계값 (BVA) 핵심 |
|---|---|---|
| 재무 체력 일반 (부채비율) | `IND-FH-G-*` | 100% 미만 A, 100~300% B, 300% 이상 C |
| 재무 체력 스타트업 (런웨이) | `IND-FH-S-*` | 18개월 이상 A, 12~18개월 B, 12개월 미만 C |
| 성장성 일반 / 스타트업 | `IND-GR-G-*`, `IND-GR-S-*` | 15% / 50% 이상 A, 0 이상 B, 감소 C |
| 수익성 일반 (영업이익률) | `IND-PF-G-*` | 7% 이상 A, 3% 이상 B |
| 수익성 스타트업 (영업이익 방향) | `IND-PF-S-*` | 0 이상 A, 적자 축소 B, 같거나 확대 C |
| 고용 흐름 일반 / 스타트업 | `IND-HR-G-*`, `IND-HR-S-*` | 순증 여부 x 퇴사율(연 20%, 월 3%, 월 5%) |
| 보상 | `IND-CP-*` | 업종 평균 +10% 이상 A, -10% 이하 C |
| 근속 | `IND-TN-*` | 10년 이상 A, 5년 이상 B |
| 기술 투자 일반 | `IND-TI-G-*` | 업종 구간 4개 각각의 상한과 하한 |
| 기술 투자 스타트업 | `IND-TI-S-*` | 등록 특허 3건 이상 A, 1~2건 B, 0건 C |
| 투자 단계 | `IND-FS-S-*`, `IND-FS-G-*` | 금액 조건 x 18개월 조건, 일반 기업은 항상 등급 없음 |
| 리스크 | `IND-RK-*` | 해당 없음 A, 경미 B, 해당 C |
| 정보 투명도 | `IND-TR-*` | 확인 7개 이상 A, 4개 이상 B (일반 기업은 8개 중) |
| 확인 불가 처리 | `IND-EG-*` | 이유(`not_disclosed`, `no_source`, `fetch_failed`)가 그대로 전달 |
| 업종 구간 (KSIC) | `IND-KSIC-*` | 코드 12개가 4개 구간으로 나뉜다 |

## 근거 확인: 테스트가 보증하는 것

- 등급이 나온 칸은 "어느 기준으로 매겼는지"(근거 문구)가 비어 있지 않고, 기준값이 문구에 들어 있다
- 값이 없으면 등급을 주지 않고 이유를 반드시 붙인다 (일반 기업의 투자 단계만 "등급 없음"이라 이유 없음)
- 경계값은 "N 이상" 쪽 등급이다 (부채비율 정확히 100% = B, 매출 증가율 정확히 15% = A)
- 퇴사율을 모르면 고용 흐름은 A가 될 수 없다 (최대 B)
- 같은 입력이면 항상 같은 결과다

## 테스트가 정말 버그를 잡는지 (변이 확인, 2026-11-20)

기준 코드를 일부러 한 곳씩 틀리게 바꿔서 테스트가 실패하는지 봤다. 5곳 모두 실패로 잡혔다.

| 일부러 낸 버그 | 결과 |
|---|---|
| 부채비율 경계 `< 100`을 `<= 100`으로 | 잡힘 (1개 실패) |
| 스타트업 영업이익 0을 흑자로 안 침 | 잡힘 (1개 실패) |
| 보상 +10% 경계 `>=`를 `>`로 | 잡힘 (1개 실패) |
| 정보 투명도 A 기준 7개를 8개로 | 잡힘 (2개 실패) |
| 투자 18개월 경계 `<=`를 `<`로 | 잡힘 (2개 실패) |

## 에이전트 루프 테스트 (AGT, 2026-11-20)

LLM 응답을 가짜로 바꿔 넣어서 크레딧 없이 루프의 규칙을 검사한다.

| 케이스 | 기법 | 확인하는 것 |
|---|---|---|
| AGT-01~03 | 상태 전이 | 후보 1곳이면 바로 카드, 2곳이면 후보 칩, 도구 없이 답하면 그 문장 |
| AGT-04~06 | 경계값 | 호출 8회까지 실행, 9회째에서 멈추고 `limit` 로그. 한 응답의 도구 여러 개도 각각 센다 |
| AGT-07~11 | 오류 추정 | 없는 도구, 잘못된 인자, API 연결 실패, 알 수 없는 오류, 거절. 전부 멈추지 않고 대신 답한다 |
| AGT-12~14 | 규칙 | 카드 숫자는 코드 계산과 같고 LLM 문장이 섞이지 않는다. LLM에 대표자 이름을 보내지 않는다. 강제 도구 선택 없음 |

- 변이 확인: 상한 비교를 `>`에서 `>=`로, 도구 결과에 대표자 이름 추가, 오류 표시(`is_error`) 끄기. 3곳 모두 잡혔다
- 실제 API는 테스트에서 부르지 않는다. 사람이 `USE_AGENT=true`로 켜서 확인한다

## 합격 기준과 결함 보고

- PR 전: `npm test`, `npm run lint`, `npm run build`가 모두 통과해야 한다. 화면 흐름을 건드렸으면 `npm run test:e2e`도
- 결함을 찾으면 PR이나 이슈에 이 형식으로 적는다
  - 케이스 ID, 입력, 기대 결과, 실제 결과, 재현 순서, 심각도(상: 등급이 틀림 또는 규칙 위반, 중: 화면 깨짐, 하: 문구)
- 기준표나 등급 로직을 바꾸면 registry, 테스트, 회귀 표(`REG`)를 **같은 PR에서** 같이 고친다

## 실행 방법

```bash
npm test                # 단위·통합·회귀 (약 1초)
npm run test:verbose    # 케이스 ID와 입력, 기대 등급을 한 줄씩 보기
npm run test:e2e        # 화면 흐름 (개발 서버를 3100번 포트로 따로 띄움)
```

- E2E는 컴퓨터에 설치된 Chrome을 쓴다(내려받기 없음). Chrome이 없으면 `npx playwright install chromium` 후 `PW_CHANNEL=chromium npm run test:e2e`
- E2E 서버는 별도 빌드 폴더(`.next-e2e`)를 써서, 이미 켜 둔 `npm run dev`(3000번)와 부딪히지 않는다
