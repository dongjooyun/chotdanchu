# 깃 협업 규칙

자세한 단계별 튜토리얼(윈도우 세팅, 첫 PR, 자주 쓰는 프롬프트)은 팀 노션 "깃허브 협업 튜토리얼"에 있다. 이 문서는 요약본이다.

## 한 장 요약

```
git pull            최신 main 받기 (작업 시작 전 매번)
git switch -c 이름/작업내용     내 작업용 브랜치 만들기
(작업)
git add .
git commit -m "종류: 무엇을 했는지"
git push -u origin 이름/작업내용
gh pr create        PR 열기 (또는 GitHub 웹에서)
→ 리뷰 → main에 합치기 → git switch main → git pull
```

Claude Code에게는 이렇게만 말해도 된다: "지금 변경사항으로 브랜치 만들고 커밋하고 PR까지 올려줘."

## 브랜치

| 규칙 | 예 |
|---|---|
| `이름/작업내용` | `junoh/matchup-card-ui`, `dongju/dart-tool` |
| 한 브랜치에 한 가지 작업 | 카드 UI와 데이터 수집을 한 브랜치에 섞지 않기 |
| main에 직접 push 금지 | 항상 PR로 합치기 |

## 커밋 메시지

`종류: 무엇을 했는지`

| 종류 | 언제 |
|---|---|
| feat | 새 기능 |
| fix | 버그 수정 |
| design | 화면, 스타일 |
| data | 목업 데이터, 수집 스크립트, 역량 사전 |
| docs | 문서 |
| chore | 설정, 패키지 |

## PR

- 제목: 커밋 메시지와 같은 형식
- 본문 3줄: 무엇을 / 왜 / 어떻게 확인했나 (화면 변경은 스크린샷)
- 리뷰어: 서로. 급하면 셀프 머지하고 카톡으로 알리기

## 역할별 주로 만지는 곳 (예정)

| 사람 | 폴더 |
|---|---|
| 준오 (디자인) | `app/`의 화면, `components/` |
| 준오 (데이터) | `data/mock/`, `data/competencies/`, 수집 스크립트 |
| 동주 | `lib/agent/`, `lib/tools/`, API 라우트 |

같은 파일을 동시에 고치면 충돌이 나기 쉬우니, 큰 파일을 건드릴 땐 카톡으로 한마디 하기.
