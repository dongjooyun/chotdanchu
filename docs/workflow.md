# 깃 협업 규칙

자세한 단계별 튜토리얼(윈도우 세팅, 첫 PR, 자주 쓰는 프롬프트)은 팀 노션 "깃허브 협업 튜토리얼"에 있다. 이 문서는 요약본이다.

## 팀 규칙 3가지

| 규칙 | 왜 |
|---|---|
| **기능 하나 = 브랜치 하나.** 항상 최신 main에서 새 브랜치를 만들어 시작 | 서로의 작업이 섞이지 않고, 망쳐도 main은 멀쩡함 |
| **커밋은 조각조각, 자주.** 기능이 끝날 때 한 번이 아니라 의미 있는 한 걸음마다 | 어느 시점으로든 되돌릴 수 있음 |
| **main에 바로 합치지 않는다.** push 후 PR을 열고, 동주가 확인·승인하면 merge | 실수가 main에 들어가기 전에 한 번 거름 |

## 흐름

```
git switch main && git pull           최신 main 받기 (작업 시작 전 매번)
git switch -c 이름/작업내용             새 브랜치
(작업 조금) → git add . → git commit -m "종류: 한 일"   ← 여러 번 반복
git push -u origin 이름/작업내용
gh pr create --reviewer dongjooyun     PR 열기
→ 동주 리뷰 → (수정 요청 시 같은 브랜치에 커밋 추가 후 push) → 승인 → merge
git switch main && git pull           다음 작업 준비
```

Claude Code에게는 이렇게 말하면 된다.

- 시작: "main 최신판 받고 junoh/작업이름 브랜치 만들어줘"
- 중간중간: "지금까지 한 거 커밋해줘"
- 끝: "push하고 동주를 리뷰어로 PR 올려줘"

## 커밋 크기 예시

| 너무 큼 | 적당함 |
|---|---|
| `feat: 맞대결 기능 완성` (파일 12개) | `feat: 맞대결 카드 컴포넌트 뼈대` |
| | `design: 카드 등급 배지 색상` |
| | `feat: 카드 클릭 시 선택 기록` |
| | `fix: 모바일에서 카드가 세로로 쌓이는 문제` |

## 커밋 메시지

`종류: 무엇을 했는지`

| 종류 | 언제 |
|---|---|
| feat | 새 기능 |
| fix | 버그 수정 |
| design | 화면, 스타일 |
| data | 목업 데이터, 수집 스크립트, 역량 사전 |
| docs | 문서 |
| chore | 설정, 패키지 |

## PR

- 제목: 커밋 메시지와 같은 형식
- 본문 3줄: 무엇을 / 왜 / 어떻게 확인했나 (화면 변경은 스크린샷)
- 리뷰어: dongjooyun. 승인 전 merge 금지
- 수정 요청을 받으면 같은 브랜치에 커밋을 더해 push (새 PR 만들지 않기)

## 역할별 주로 만지는 곳 (예정)

| 사람 | 폴더 |
|---|---|
| 준오 (디자인) | `app/`의 화면, `components/` |
| 준오 (데이터) | `data/mock/`, `data/competencies/`, 수집 스크립트 |
| 동주 | `lib/agent/`, `lib/tools/`, API 라우트 |

같은 파일을 동시에 고치면 충돌이 나기 쉬우니, 큰 파일을 건드릴 땐 카톡으로 한마디 하기.
